## 2. F01：主剑缩放错误

目标：第 0 把剑逐渐放大到 6，普通剑逐渐放大到 1.5。

实际：每把剑都读取并写回同一个 `userData.currentScale`。普通剑处理 499 次后，把这一帧的共享值拉回到 1.5。下一帧主剑仅执行一次 `lerp(约1.5,6,0.01)`，结果仍接近 1.545。

证据：桌面 500 把的浏览器实例矩阵读数中，主剑约 `1.545001864`、第二把约 `1.544101834`、末把约 `1.500001907`；与独立的循环数值复现吻合。

修复建议：为每个实例维护独立的 `Float32Array` 缩放状态，或者明确维护主剑与普通剑两类状态。光环跟随相应实例缩放。

验收：连续保持大庚模式时，主剑按设定时间逼近 6，普通剑逼近 1.5；退出大庚后各自平滑恢复 1；剑数 300 和 500 时一致。

## 3. F02：帧率影响运动结果

位置推进每帧使用固定 `delta=1/60`，阵型目标与雷电闪烁使用时钟真实秒数，缩放与相机又使用固定帧插值系数。低帧率设备会同时出现追赶能力变弱、过渡变慢和视觉节奏不一致。

修复建议：统一时间策略。采用实际 dt 时，在长帧场景设置合理上限；平滑改为指数衰减。若坚持固定物理步长，则使用累积器，并对更新次数设上限。

验收：对 30 / 60 / 120fps 输入相同的时间序列，比较相同真实时刻的到达距离、相机距离及缩放；预设容差后再比较。未测得这些结果前，不写“各设备相同丝滑”的结论。

## 4. F03–F04：生命周期和错误恢复

当前成功路径可运行，但摄像头在模型加载前已经开启，后续失败不会停止 tracks；组件卸载也没有显式停止流、关闭识别器和清理全局引用。单例 Promise 还会保留旧视频绑定。

UI 将 `<video>` 设为 `opacity:0`，准备状态只影响这个不可见元素的边框。初始化失败通常仍显示“等待手势”，用户无法知道是权限、加载还是设备问题。catch 虽清空 Promise，却没有触发重试的交互。

修复建议：

1. 服务显式管理 `idle / loading / ready / error / stopped`、错误信息及当前资源。
2. 为初始化和销毁提供配对接口；失败 / 卸载时停止所有流 tracks、关闭识别器并重置检测时间。
3. 区分视频元素绑定与识别器单例；重新挂载时能够重新绑定或重建。
4. UI 显示初始化阶段、具体失败原因和重试按钮；根据实际需要增加显式启动摄像头动作。
5. 为等待视频数据、模型创建与自动播放失败设计可恢复分支。

开发入口开启了 StrictMode，effect 清理和重复调用必须可承受。当前单例缓解了部分重复初始化，但不能替代资源所有权设计。

验收：拒绝权限、模型路径返回错误、初始化后卸载再挂载、切换摄像头、视频中断恢复均有明确状态，且不会留下多余流或旧节点引用。

## 5. F05、F10：识别规则与确认时序

先由产品规则决定“单食指”究竟代表什么，再调整判断顺序和文档，避免只改提示。现有手枪手势与双指规则可以继续保留。

对 `getAngle` 增加关键点有效性、零向量和余弦范围保护。无效帧应进入未知 / 无追踪状态，不宜默认为护盾。对部分关节弯曲、侧手、左右手和遮挡收集真实样本，不能以合成点测试替代真实识别质量评估。

防抖应使用连续有效观测或明确容忍丢帧的时间窗口；追踪丢失超过阈值时重置候选计时。视频长时间没有新帧时，应更新追踪状态。

验收：包括单食指、手枪、双指、握拳、张掌、摇滚，以及“候选出现 → 手消失 → 再出现”的序列。若要求连续 250ms，消失期间不得累计进有效保持时间。

## 6. F06–F08：阵型切换与分布

追踪丢失建议采用独立的有效渲染模式，统一驱动位置、速度、朝向、缩放、特效和相机。这样可保留上一识别状态用于恢复，同时避免“位置走游龙，速度仍是护盾”的混合。

游龙历史容量建议由剑数与采样间隔共同确定；更稳妥的方式是距离或弧长重采样。预测延伸应按时间或手部运动设计上限，并避免长期用预测点污染原始采样。

大庚如确实要求固定 10 层，可通过 `layer=floor(j×10/effectiveCount)` 分配层数，再给每层计算起始索引和容量。也可显式分摊整除余数。不要只把 `floor` 改成 `ceil` 就认为每层的闭合角度问题已经解决。

验收：剑数为 300、500 和非默认值时，层数正确、每层角度分布闭合、所有剑均分配有效目标；游龙末端没有因夹取历史下标形成大量同点目标。

## 7. F09：WASM 兼容性

本地两份 SIMD 文件的 SHA-256 与锁定 MediaPipe 包内同名文件不同，单凭这一点不能断言一定不兼容。本次 Chrome + 软件 WebGL 环境已成功创建识别器。

已确认的资源缺口是：锁定 SDK 的 resolver 在 SIMD 探测失败时会选择 `vision_wasm_nosimd_internal.js/.wasm`，但 `public/models/wasm/` 没有这两个文件。该分支没有完整的本地资源交付。

修复建议：从明确匹配的已锁定 SDK 包中同步需要的运行时资源，记录版本和摘要；完整提供 resolver 可能选择的变体，或明确限定支持环境并展示失败原因。验证 GPU delegate 不可用时是否需要 CPU 回退。

验收：SIMD 支持与不支持分支均能加载正确资源；目标浏览器能执行推理；若某类设备不支持，页面明确展示实际原因。现有成功记录不外推到所有 Safari、Android 或内置浏览器。

## 8. F11–F13：相机、性能与路径

相机应依据视野角与 aspect，从完整包围体计算距离，并给放大主剑、法阵和外圈留边。竖屏提示只是建议，不是构图适配算法。

性能方面，已有实例化、TypedArray 线段缓存和视频帧去重，基础方向合理。但识别与大量向量对象分配都处于渲染主线程，Bloom 和最高 DPR=2 又增加像素处理成本。建议先采样真实设备的帧时间与检测耗时，再选择限流、Worker、降低 DPR、分档后处理或复用临时向量；当前没有证据支持某一项一定是首要瓶颈。

路径方面，使用统一的资源基路径生成器并测试根路径和子路径。静态部署还需把模型目录与 JS/CSS 同时交付。

验收：横 / 竖屏、多屏幕比例下观察完整阵型；记录实际帧率与模型检测耗时；部署到约定子路径后模型请求地址正确。

## 9. F14–F15：工程与界面一致性

补齐匹配现有 ESLint 版本的配置，再实际执行检查。不能仅删除 `lint` 脚本或忽略退出码就认为质量门禁恢复。当前的类型构建检查已经通过，应保留。

状态标签 `StatusIndicator` 未处理 DAGENG，落到默认“游龙阵型”；底部提示又正确显示“大庚剑阵”，同屏不一致。可以集中维护模式名称、颜色和提示，消除重复 switch。

React 版提示中的 `�` 是源码已有字符，不是本次终端显示造成；浏览器页面也能看到。清理模板资源和未使用依赖时，以实际 import 和构建结果确认；把 `formationRadius`、`dragonDensity` 接到实际算法或删除误导配置。

## 10. 建议实施次序

1. **先修核心行为与可恢复运行**：F01、F02、F03、F04，补齐可见的状态和失败恢复。
2. **再统一交互与阵型规则**：F05–F08、F10、F15，明确待机模式、手势含义和分布规则。
3. **完成目标环境交付**：F09、F11、F13、F14，补齐资源、适配、路径与检查配置。
4. **用测量决定性能优化**：F12 及向量复用、轨迹缓冲、DPR / Bloom 分档。

每阶段只针对真实修改运行必要验证：算法改动关注分布和时间一致性；生命周期改动关注权限、失败和卸载恢复；视觉改动关注目标设备和构图。没有必要为纯说明文字或模板资源清理增加模拟业务实现的测试。
